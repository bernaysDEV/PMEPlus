# نتائج مراجعة الإصلاحات الأمنية

تاريخ المراجعة: 2026-05-06  
النطاق: مراجعة الإصلاحات الأخيرة على الثغرات الأمنية السابقة  
الحالة: توجد إصلاحات مهمة أُنجزت، لكن بقيت ملاحظات تحتاج معالجة

## Finding 1: Mobile password reset leaks the reset code

الأولوية: P0  
الملف: `server/routes/mobileApiRoutes.ts`  
الأسطر: 1314-1321

### الوصف

مسار استعادة كلمة المرور للموبايل يعيد `resetCode` و`userId` في استجابة `forgot-password`.

هذا يعني أن أي شخص يعرف بريد مستخدم يستطيع طلب:

```text
POST /api/v1/auth/forgot-password
```

ثم يحصل على رمز إعادة التعيين مباشرة من الاستجابة، وبعدها يمكنه استخدامه لإعادة تعيين كلمة المرور بدون الوصول إلى البريد الإلكتروني.

### الأثر

- الاستيلاء على حسابات مستخدمي تطبيق الموبايل.
- تجاوز كامل لقناة البريد الإلكتروني التي يفترض أن تكون عامل إثبات الملكية.
- كشف وجود المستخدم أو بيانات تساعد على الاستهداف إذا اختلفت الاستجابة.

### الحل المقترح

1. حذف `resetCode` من الاستجابة نهائياً.
2. حذف `userId` من الاستجابة.
3. توحيد الاستجابة سواء كان الحساب موجوداً أم لا.
4. إرسال الرمز فقط عبر البريد أو القناة الموثوقة.
5. تخزين الرمز كـ hash بدلاً من plaintext.
6. إضافة حد محاولات صارم للتحقق من الرمز.

## Finding 2: Reset OTP uses Math.random

الأولوية: P1  
الملف: `server/routes/mobileApiRoutes.ts`  
الأسطر: 721-724

### الوصف

رموز التفعيل واستعادة كلمة المرور للموبايل تُولّد عبر:

```ts
Math.random()
```

وهذا غير مناسب للرموز الأمنية، لأن `Math.random` ليس مولداً عشوائياً مخصصاً للأمان.

### الأثر

- قابلية أعلى للتخمين أو التنبؤ مقارنة بـ cryptographic randomness.
- زيادة خطر brute force على رموز قصيرة من 6 أرقام.

### الحل المقترح

1. استبدال التوليد بـ:

```ts
crypto.randomInt(100000, 1000000).toString()
```

2. أو استخدام رمز أطول عبر:

```ts
crypto.randomBytes(16).toString("hex")
```

3. تخزين hash فقط للرمز.
4. إضافة عدد محاولات تحقق محدود.
5. إضافة expiration قصير.

## Finding 3: APM auth middleware is registered after APM routes

الأولوية: P2  
الملف: `server/index.ts`  
الأسطر: 625-656

### الوصف

مسارات:

```text
GET /api/apm/stats
POST /api/apm/reset
```

أصبحت محمية بدالة تعتمد على:

```ts
req.isAuthenticated
```

لكن هذه المسارات مسجلة قبل تركيب `setupAuth(app)`. في Express ترتيب تسجيل middleware والمسارات مهم، لذلك `req.isAuthenticated` غالباً لن يكون موجوداً عند تنفيذ `requireApmAccess`.

### الأثر

- المسارات قد ترجع `401` دائماً حتى للمستخدم الإداري.
- تعطّل وظيفة المراقبة بدلاً من حمايتها بشكل صحيح.

### الحل المقترح

1. نقل تسجيل مسارات APM بعد:

```ts
await setupAuth(app)
```

2. أو تركيب session/passport قبل هذه المسارات.
3. الإبقاء على شرط صلاحية:

```text
system.manage_settings
```

## Finding 4: Public AI chat still lacks the AI limiter

الأولوية: P2  
الملف: `server/routes.ts`  
الأسطر: 15883-15924

### الوصف

المساران العامان:

```text
POST /api/ai/chat
POST /api/en/chat
```

يستدعيان خدمات ذكاء اصطناعي ومُستثنيان من CSRF كمسارات عامة، لكنهما لا يمران على `aiLimiter` الخاص بالمسارات المكلفة.

### الأثر

- استنزاف رصيد خدمات AI.
- ضغط على الخادم عبر طلبات عامة متكررة.
- الاعتماد فقط على limit عام واسع لا يكفي لهذه المسارات.

### الحل المقترح

1. إضافة `aiLimiter` مباشرة على المسارين.
2. أو تركيب limiter قبل `registerRoutes` لهذه المسارات المحددة.
3. وضع حدود حجم للرسالة ومدة session/visitor.
4. مراقبة معدل الفشل وتفعيل حماية إضافية عند الإساءة.

## Finding 5: XLSX timeout does not bound the synchronous parse

الأولوية: P2  
الملف: `server/data-parser.ts`  
الأسطر: 75-83

### الوصف

تمت إضافة `checkBudget()` بعد:

```ts
XLSX.read(buffer, ...)
```

لكن `XLSX.read` عملية synchronous. إذا تسبب ملف ضار أو ثغرة ReDoS بتعليق المعالجة داخل `XLSX.read`، فلن يصل التنفيذ إلى `checkBudget()` أصلاً.

### الأثر

- إمكانية تعليق event loop.
- DoS عبر ملف Excel ضار.
- بقاء خطر `xlsx` قائماً رغم إضافة فحص وقت بعدي.

### الحل المقترح

1. عزل معالجة Excel في worker أو process منفصل.
2. تطبيق timeout خارجي يقتل worker/process عند تجاوز المهلة.
3. أو استبدال `xlsx` بمكتبة أكثر أماناً.
4. أو تعطيل Excel مؤقتاً والاكتفاء بـ CSV/JSON للملفات غير الموثوقة.
5. الاستمرار في حدود الحجم والصفوف والأعمدة، لكنها لا تكفي وحدها.

## ملخص سريع

الأخطر حالياً هو `Finding 1` لأنه يسمح عملياً بتجاوز استعادة كلمة المرور في Mobile API. يليه `Finding 2` لأن الرموز الأمنية يجب ألا تعتمد على `Math.random`. بقية الملاحظات مهمة لكنها أقل إلحاحاً من تسريب رمز reset.
